# Импорт карт для Virtual TTG

Внешний модуль [Virtual TTG](https://github.com/TTG-Club/vttg): переносит карту
из редактора прямо в сцену мира — вместе со стенами, дверями и светом.

Работает с форматом **Universal VTT** (`.dd2vtt`, `.uvtt`, `.json`). Его
экспортирует **Dungeondraft** (File → Export → Universal VTT), а также Dungeon
Alchemist, Arkenforge и другие редакторы — поэтому парсер один на всех.

## Что импортируется

| Из файла карты | Во что превращается | Примечание |
|---|---|---|
| `image` (base64) | фон сцены | сервер перекодирует в WebP; размеры сцены берутся по РЕАЛЬНО загруженной картинке |
| `resolution.pixels_per_grid` | размер клетки (`custom`) | масштаб пересчитывается, если сервер сжал фон |
| `line_of_sight` | стены | каждый отрезок ломаной — отдельная стена; блокируют движение, зрение и свет |
| `objects_line_of_sight` | стены | мебель и колонны, тоже по отрезку; почти замкнутый контур замыкается точно; отключаемо |
| `portals` | двери / окна | по умолчанию — как в редакторе: закрытый портал — дверь, открытый — окно; можно выбрать один тип для всех |
| `lights` | источники света | `range` (клетки) → радиусы в пикселях, `intensity` приводится к 0–1 |
| `environment.baked_lighting` | свет и тьма выключены | свет уже нарисован на картинке — второй раз его не накладываем |

Сцена создаётся **скрытой** — покажите её игрокам, когда закончите правки.

### Что НЕ переносится

- **Сетка в координатах файла.** Смещение сетки (`offsetX`/`offsetY`) всегда
  нулевое: редакторы экспортируют карту ровно по клеткам, и подгонять нечего.
  Если фон всё же едет — поправьте сетку инструментом подгонки на сцене.
- **Токены, мебель как объекты, подписи.** В Universal VTT их нет: формат
  отдаёт только картинку, геометрию зрения, порталы и свет.
- **Многоэтажные карты.** Формат — один слой на файл; этажи экспортируются
  отдельными файлами, каждый импортируется своей сценой.

## Установка

```bash
pnpm install
pnpm build
node scripts/installToWorld.mjs "D:/путь/к/папке/мира"
```

Модуль попадёт в `<папка мира>/modules/map-import/`. Дальше в мире:
настройки → «Управление модулями» → «Перезагрузить мир». В левом тулбаре сцены
у мастера появится кнопка импорта.

Проверить импорт можно без Dungeondraft: `pnpm make:sample` рисует настоящий
`.dd2vtt` — комнату 8×6 клеток со стенами, дверью, окном, мебелью и двумя
огнями (`fixtures/sample.dd2vtt`). На нём же держатся тесты парсера.

### Хэш-пин: почему модуль исчезает после пересборки

Приложение фиксирует хэш кода модуля при первом появлении
(`<данные установки>/installed-modules.json`) и дальше требует точного
совпадения — так ловится подмена файлов уже установленного модуля. Для
разработчика это значит, что **любая пересборка выглядит как подмена**: сервер
молча перестаёт отдавать манифест клиенту, и модуль пропадает из «Управления
модулями» вовсе. В логе мира это видно строкой:

```
[ModuleSettings] Модуль "map-import" не отдан клиенту: код не совпадает
с зафиксированным при установке
```

Снять пин из интерфейса нечем, поэтому это делает `installToWorld.mjs`: он
удаляет записи `<мир>:map-import` из реестра, и ближайшее чтение пиннит новую
сборку заново. Если приложение хранит данные в нестандартном месте, путь можно
подсказать: `VTTG_DATA_PATH="D:/.../Data" node scripts/installToWorld.mjs …`.

## Требования к хосту

| Что | Версия | Где объявлено |
|---|---|---|
| Приложение VTTG | не ниже **0.9.539** | `compatibility` в `module.json` |
| Игровая система | любая | `compatibleSystems` не задано — модуль универсальный |

0.9.539 — первая версия, где в API модулей есть запись в сцену и файлы мира
(разрешения `scene-write` и `assets`). В более старом приложении модуль не
прячется молча: в «Управлении модулями» его карточка приглушена и подписана
причиной («Нужна версия приложения не ниже…»).

Модуль пользуется:

- `api.scene.createScene` — создаёт сцену и ждёт подтверждения сервера;
- `api.scene.addWalls` / `api.scene.addLights` — стены, двери, окна и свет;
- `api.scene.openScene` — открыть готовую сцену у мастера;
- `api.assets.upload` / `api.assets.resolveUrl` — перенос фона в файлы мира и
  измерение его реального размера;
- `api.scene.isGM` — импорт предлагается только мастеру.

Полный контракт — в `docs/MODULES.md` репозитория хоста. Права проверяет
сервер: сцены, стены и свет он принимает **только от мастера**, поэтому у
игрока кнопки нет вовсе, а вызовы API всё равно были бы отклонены. Настройки
мастера импорта (галочки) общие на мир и пишутся только от мастера.

Система мира не ограничена намеренно: карта — это фон, геометрия и свет, в ней
нет ничего от правил игры.

### Повторный вход в мир

При выходе из мира хост снимает модуль целиком, а при входе исполняет
`client.js` **заново**. Поэтому в сборке не должно быть `const`/`let`/`class`
верхнего уровня — повторное исполнение классического скрипта упало бы на
повторном объявлении. Vite собирает модуль в IIFE (`(function(vue){…})(Vue)`),
так что всё объявленное живёт внутри функции; не меняйте формат сборки.

## Разработка

```bash
pnpm dev            # пересборка при изменениях
pnpm type-check     # проверка типов
pnpm test           # тесты парсера и конвертера
pnpm make:sample    # образец карты fixtures/sample.dd2vtt
```

Сборка — IIFE (`dist/client.js` + `dist/styles.css`): хост грузит модуль обычным
`<script>`, а Vue берётся из `globalThis.Vue` хоста, чтобы компоненты работали на
том же экземпляре Vue, что и приложение.

Структура:

```
src/
├── main.ts              регистрация модуля, кнопка в тулбаре
├── types/vttg.ts        типы хостового API (копия контракта из docs/MODULES.md)
├── uvtt/schema.ts       zod-схема формата
├── uvtt/parse.ts        чтение файла, сводка, распаковка base64-картинки
├── uvtt/convert.ts      геометрия: клетки → пиксели, полилинии → стены
├── import/runImport.ts  сценарий импорта целиком
└── ui/                  мастер импорта и кнопка тулбара
```

### Релиз для каталога

Тег `vX.Y.Z` собирает модуль и публикует архив `map-import.zip` в релиз
GitHub (`.github/workflows/release.yml`); тег обязан совпадать с версией в
`module.json`, иначе сборка падает. На этот архив указывает поле `download`
манифеста, и оттуда его скачивает VTTG при установке модуля из каталога.

```bash
git tag v0.2.1 && git push origin v0.2.1
```

## Тонкости формата

- **Стена в VTTG — ровно один отрезок.** Рендер стен и расчёт зрения хоста
  берут из `points` только первые четыре числа. Universal VTT же отдаёт стены
  ломаными на десятки точек (полукруглая стена — это одна ломаная), и такая
  ломаная, отданная одной стеной, рисовалась бы одними вершинами, а зрение и
  движение перекрывал бы лишь её первый отрезок. Поэтому каждая ломаная
  режется на отрезки — стен в сцене получается в разы больше, чем в сводке
  файла, и это нормально.
- **Двери или окна.** Формат их не различает — у портала есть только
  геометрия и признак «закрыт». Dungeondraft отдаёт окна открытыми, а двери
  закрытыми, на этом и построен режим «как в редакторе». Это догадка, а не
  данные формата: дверь, оставленная в редакторе открытой, станет окном —
  тогда выберите тип вручную.
- **Координаты** в Universal VTT заданы в КЛЕТКАХ, а не в пикселях. Часть
  редакторов пишет их относительно экспортированного куска, часть — в координатах
  исходной карты; модуль определяет это по выходу точек за границы и при
  необходимости вычитает `map_origin`.
- **Цвет света** — hex-строка Godot (`RRGGBBAA`, альфа В КОНЦЕ), потому что
  Dungeondraft построен на Godot. Берутся первые шесть символов.
- **Сжатие фона.** Сервер мира всегда перекодирует изображения в WebP и ужимает
  стороны больше 8192 px. Поэтому масштаб считается по загруженной картинке, а не
  по данным файла — иначе стены разъезжаются с фоном.
